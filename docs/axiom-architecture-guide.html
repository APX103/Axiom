1. Axiom 是什么

Axiom 是一个本地优先的科研 AI 工作台。它把 LLM 的推理能力、学术数据检索、代码执行、文件编辑和版本化管理，打包成一个可以运行在 macOS 桌面上的应用。

它的后端内核是 axiom-core（对原版 Operon 的 clean-room Python 重实现），前端是 React + Vite，桌面壳用 Tauri v2（Rust）把前后端打包成一个可分发应用。所有会话、工作区文件、SQLite 数据库都保存在本地机器上，LLM 调用则走兼容 OpenAI 协议的云端或本地模型。

本地优先

数据、工作区、SQLite 全在本地；支持把数据目录软链到 SSD。

云端推理 + 本地执行

LLM 只负责推理，所有工具、代码、文件操作都在本地完成。

学术工作流

内置 OpenAlex 论文检索、引用图扩展、DOI 校验、LaTeX 综述渲染。

可扩展 Skill

通过 SKILL.md + 可选 kernel.py 给 Agent 注入领域策略。

关键设计哲学

所有“状态”尽量落在本地（SQLite、工作区文件、Artifact 版本链），LLM 只作为无状态的推理引擎。这让 Axiom 更像一个“会自己调用工具的本地科研 IDE”，而不是一个纯聊天应用。

3. Agent 主循环：一次请求的生命周期

当用户在工作台输入一句话（例如“帮我写一份关于 LLM 推理时计算的综述”），后端会启动一次 Agent Run。它的核心在 axiom_core/agent/runner.py 的 Agent._run_loop()。

1
Session.prepare()

创建根 frame、初始化 ToolContext（workspace、api_keys、ArtifactStore、SkillCatalog、MemoryStore、host 对象），注册内置工具，连接 MCP servers。

2
记忆召回

用用户输入对三层记忆（profile / project / frame）做 BM25 召回，把相关记忆以 harness-notice 注入上下文。

3
构建 System Prompt

build_system_prompt() 把 floor 规则、代码执行规则、学术诚信规则、skill 指令、计划状态、记忆摘要拼成最终 system prompt。

4
调 LLM

优先走流式，每个 text/thinking delta 实时推给前端；返回 tool_use 或自然文本。

5
执行工具

ToolRouter 并发执行 tool_use，回填 tool_result，继续下一轮。

6
自然完成 / Reviewer 终审

无 tool_use 时进入完成路径，Verifier 可选做 terminal barrier 审查，发现 fabricated citation 等问题会 veto 并要求 Agent 修复。

Rolling Compact

当上下文接近模型窗口上限时，axiom_core/compact/ 会对历史消息做 L1/L2 折叠与摘要，避免爆窗。它会在每轮调 LLM 前检查并触发。

4. 论文搜索策略

Axiom 没有硬编码一个独立的“多轮搜索引擎”。它的搜索能力由三层组合而成：

  1. 单轮工具层：OpenAlex、DuckDuckGo web_search、Crossref 校验。
  2. Skill 策略层：literature-review skill 通过提示词让 Agent 自己驱动“首轮搜索 → 取 Top-K → 引用图扩展 → 验证 → 写作”的迭代流程。
  3. 存储层：结果需要 Agent 主动调用 save_artifacts 或 write_memory 才会持久化。

4.1 数据源与工具

工具 / API 代码位置 作用
OpenAlex axiom_core/tools/builtins/openalex.py search_papers 关键词检索；fetch_paper 按 DOI 取详情。支持 relevance / cited_by_count / publication_date 排序。
Crossref skills/skills/literature-review/kernel.py crossref_lookup 自由文本引用找 DOI；verify_dois 校验 DOI 真实性并检测撤稿。
Web 搜索 axiom_core/tools/builtins/web.py web_search / fetch_url 基于 DuckDuckGo，补充最新网页或灰色文献。
MCP 连接器 axiom_core/mcp/ 可接入 PubMed、Semantic Scholar、bioRxiv、ClinicalTrials.gov 等外部学术 MCP server。
OpenAlex 需要 API Key

kernel.py 中的 search_openalex / expand_citations 强制要求 OPENALEX_API_KEY，匿名调用会直接报错。Crossref 可不带 key，但配置 contact email 会进入 polite pool。

4.2 多轮/迭代搜索的实现

多轮搜索不是由代码循环驱动，而是由 literature-review skill 的提示词策略驱动，Agent 自主决定何时扩展、何时停止。标准流程如下：

flowchart LR A[用户查询] --> B[首轮 sweep] B --> C[取 Top 2-3 命中] C --> D[backward:
references] C --> E[forward:
cited_by] D --> F[合并 + 去重] E --> F F --> G[verify_dois 校验] G --> H[按主题合成写作] H --> I[save_artifacts]

图 3：literature-review skill 驱动的迭代搜索流程

其中最关键的一步是 expand_citations(doi)，它在 skills/skills/literature-review/kernel.py 中实现：

def expand_citations(doi: str, n_backward: int = 50, n_forward: int = 15) -> dict:
    # 1. 通过 DOI 拿到 OpenAlex work_id
    # 2. /works?filter=cited_by:<work_id>  取该文的参考文献（向后一步）
    # 3. /works?filter=cites:<work_id>     取引用该文的后续论文（向前一步）
    # 4. 默认按 cited_by_count:desc 排序
    # 5. 若带 authorships 的 select 失败，降级重试不带 authorships
    return {"references": [...], "cited_by": [...]}
代码片段：expand_citations 的核心逻辑

这一步的价值在于：

  • Backward（references）：帮你找到该领域奠基的 seminal paper。
  • Forward（cited_by）：帮你找到最新进展、扩展或争议工作。

去重靠 DOI 作为唯一键；相关性选择交给 LLM 判断（skill 提示词要求“取最相关的 2–3 篇”）。也就是说，多轮搜索的“多轮”体现在 Agent 根据工具返回自主决定何时再调用一次 expand_citations 或 search_openalex，而不是系统有一个固定的 for 循环。

为什么这样设计？

把搜索策略写成 skill 提示词而不是硬编码引擎，好处是灵活：不同领域可以换不同的 MCP 数据源，Agent 能根据初步结果决定继续深挖哪个方向。代价是搜索结果的质量高度依赖 LLM 的规划和判断能力。

5. 从搜索到综述：literature-review skill

你提到的“专门用来写综述的 skill”就是 skills/skills/literature-review/SKILL.md，它配套了一个 kernel.py 提供检索/校验/格式化辅助函数。

5.1 Skill 的核心写作规范

Retrieve first, then write

任何综述类请求，第一步先做文献 sweep，答案必须建立在真实检索结果上。即使 Agent 知道答案，也要 resolve 一次 DOI，因为“一个 DOI 要么解析到真实论文，要么就是一个 fabrication”。

Synthesis, not summary

按主题组织段落，不要按论文罗列。每段第一句应该是你自己的合成观点，然后用引用支撑它。如果每段第一句都是作者名，那它只是一份带注释的参考书目。

Calibrate to evidence

区分 landmark 工作与最新进展；标注预印本；标注争议；单队列发现要说“one group reported X”，III 期 RCT 才能直接陈述。

5.2 综述生成的典型工具链

当用户说“帮我写一份关于 X 的综述”时，Agent 通常会按这个顺序调用工具：

  1. search_skills({query: "literature review"}) → 发现 literature-review skill。
  2. skill({skill: "literature-review"}) → 把 SKILL.md + kernel.py 注入上下文。
  3. search_papers / kernel.search_openalex → 首轮检索。
  4. fetch_paper → 获取单篇详情。
  5. kernel.verify_dois → 校验候选 DOI。
  6. kernel.expand_citations → 前后向引用图扩展。
  7. write_file / Python 生成 draft.md 或 main.tex + references.bib。
  8. kernel.style_pass(draft) → 确定性 lint。
  9. save_artifacts → 版本化保存。
  10. Verifier.terminal_barrier() → 最终审稿，可能要求修复。

6. Citation 机制

Axiom 内部其实有两条 citation 轨道：一条给 Markdown 综述（聊天回复 + .md artifact），一条给 LaTeX 综述论文（.tex + .bib）。

6.1 Markdown 模式

Inline citation 格式是 Markdown 链接：

[Author Year](https://doi.org/10.xxxx/xxxxxx)

渲染后显示为 (Author Year)，DOI 藏在 href 里，既方便读者点击，也方便正则提取。如果 DOI 本身含括号，必须 URL 编码为 %28 / %29，否则链接会断。

禁止的写法

不要出现 [1][2][3] 编号引用（段落重排后会错位），也不要把 (DOI: 10.xxxx/...) 作为正文可见文本。

6.2 LaTeX 模式

当前端检测到工作区有 .tex 文件时，会进入 PaperView 渲染。此时 citation 必须走 natbib：

  • Inline：\citep{key}（括号引用）或 \citet{key}（文本引用）。
  • Multiple：\citep{key1,key2}，逗号分隔无空格。
  • BibTeX key 规范：firstauthor_lastname + year + first_content_word，例如 wei2022chain、vaswani2017attention。
% main.tex
Early work on attention \citep{vaswani2017attention} established ...

% references.bib
@article{vaswani2017attention,
  title   = {Attention is all you need},
  author  = {Vaswani, Ashish and Shazeer, Noam and Parmar, Niki and others},
  year    = {2017},
  journal = {NeurIPS},
  doi     = {10.48550/arXiv.1706.03762}
}

前端 frontend/src/tex.ts 会：

  1. 解析 .tex 中的 \cite[ptp]*{...}。
  2. 按正文首次出现顺序给每个 key 编号（_citeMap[key] = number）。
  3. 把 \citep{key} 渲染成可点击的 [N] 锚点。
  4. 解析 .bib，在文末生成编号参考文献列表。

6.3 DOI 校验与风格检查

为了保证 citation 不 hallucinate，系统做了一系列校验：

函数 位置 作用
verify_dois kernel.py Crossref + doi.org 双重验证；检测 update-to 撤稿标记；拒绝含 . / .. 的伪造 DOI。
crossref_lookup kernel.py 用 author/year/title 自由文本找 DOI，避免“模式补全”一个假 DOI。
extract_dois kernel.py 从草稿中提取所有 DOI，统一喂给 verify_dois。
style_pass kernel.py 确定性正则检查：em-dash 滥用、弱化表述、过程叙述、DOI 括号未编码、标题过长、结构过平。
Verifier.terminal_barrier axiom_core/verify/verifier.py 用独立 reviewer LLM 终审，检测 fabricated citation、claim contradiction 等。
一个安全设计

verify_dois 会先检查 DOI 路径里是否包含 . / .. 空段，防止 CDN 路径归一化让伪造 DOI “看起来解析成功”。

7. Artifact 版本化存储

生成的综述文章不是普通文件，而是 Artifact。核心实现在 axiom_core/artifacts/store.py。

ArtifactStore 是三层结构：

  • artifacts：逻辑文件，可多版本。
  • artifact_versions：物理版本，含 checksum、storage_path、parent_version_id、lineage。
  • artifact_dependencies：版本间 DAG 依赖（例如 references.bib 依赖 main.tex）。

保存时通过 version_of 参数追加新版本，并用 乐观并发检测冲突（如果 latest_version_id 已变，返回 stale_base）。内存优先运行，API 服务模式下会同时写入 SQLite，启动时 load_from_db() 回放。 

save_artifacts(ctx, files=[{path: "draft.md"}])
# 返回: ![draft.md]({{artifact:<VID>}})
为什么需要 Artifact？

普通 write_file 只是写工作区文件；save_artifacts 会把它提升为带版本链、依赖 DAG、checksum 的一等产物，方便后续引用、审稿、复现和前端展示。

8. 前端如何渲染综述

前端 frontend/src/components/PaperView.tsx 负责 LaTeX 论文预览。它会从后端读取工作区中的 .tex 和同名的 .bib，交给 frontend/src/tex.ts 做轻量解析：

  • \section / \subsection / \subsubsection → <h2> / <h3> / <h4>
  • \title / \author / \date → 头部信息
  • \begin{itemize} / \item → 列表
  • $...$ / \(...\) / \[...\] → KaTeX 渲染
  • \citep / \citet / \cite → 编号引用锚点
  • .bib → 格式化参考文献列表

注意前端不做完整 LaTeX 编译，只是“够看”的渲染。用户仍然可以下载原始 .tex 到本地用完整工具链编译。

9. 关键要点总结

本地优先 + 云端推理

状态全在本地，LLM 仅作推理；Tauri 把前后端打包成 macOS App。

Agent 是调度中心

所有能力都是工具，Agent 循环负责调 LLM、执行工具、处理结果、审稿。

论文搜索 = 工具 + Skill 策略

OpenAlex/Crossref 提供单轮检索，literature-review skill 驱动迭代扩展。

多轮扩展靠引用图

expand_citations 做 1-hop 前后向扩展，找到奠基工作与最新进展。

Citation 双轨制

Markdown 用 [Author Year](doi)；LaTeX 用 \citep{key} + .bib。

校验贯穿始终

DOI 解析、撤稿检测、style_pass lint、Verifier 终审，降低 fabricated citation 风险。

给朋友的一句话

Axiom 本质上是一个“会自己查论文、写综述、做引用校验的本地科研 IDE”。它把搜索、写作、版本化、审稿串成一条流水线，而 literature-review skill 就是这条流水线的作业指导书。
